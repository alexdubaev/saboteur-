# Архитектура закрытой альфы

## Правила и состояние

[Конфигурация](../packages/config/src/index.ts) загружает указанные в [game-config.json](../data/game-config.json) каталог v2 и внутренний профиль v0. [Валидация](../packages/game-core/src/validation.ts) проверяет структуру и ссылки и вычисляет digest. Матч закрепляет каталог, профиль и digest в своём JSON-снимке. Новый матч после повтора берёт конфигурацию из предыдущего матча. Изменения правил и формата снимков требуют учёта уже сохранённых партий. [ADR 0002](adr/0002-immutable-ruleset.md).

[Game core](../packages/game-core/src/index.ts) получает доменную команду, место и RNG. `applyCommand` при успехе возвращает новый снимок с одной новой ревизией и события. `legalMoves` задаёт допустимые действия. [Граф поля](../packages/game-core/src/graph.ts) строится по связанным компонентам портов с поворотом 0° или 180°. Один тайл может содержать несколько независимых компонентов.

## Команды и восстановление

1. [HTTP и WebSocket](../apps/server/src/http.ts) принимают команды по одному [контракту](../packages/protocol/src/index.ts). Гость получает HttpOnly-cookie. Доступ к комнате определяется сессией и местом. WS проверяет origin и принадлежность к комнате.
2. [Сервис комнат](../apps/server/src/rooms.ts) блокирует строку комнаты в PostgreSQL, проверяет квитанцию, затем матч и ожидаемую ревизию. Повтор той же команды возвращает сохранённое подтверждение. Повтор ID с изменённым содержимым отклоняется. Принятие команды фиксирует снимок, безопасные события и квитанцию в одной транзакции. Дедлайны и боты обрабатываются сервером с той же блокировкой. Бот получает `PlayerView` и выбирает из доступных ходов.
3. [Проекции](../packages/game-core/src/views.ts) формируют публичное состояние и личные данные места. Полный снимок, RNG и скрытые сведения других мест остаются на сервере. Клиент получает только свою руку, текущую роль, разведку, личный счёт и допустимые ходы. Публичное раскрытие ролей, целей и итоговых очков следует фазам матча.
4. [Клиент](../apps/web/src/network.ts) отправляет команды по HTTP, при сетевом сбое повторяет тот же ID, получает персональные снимки по WS и запрашивает новый снимок после обрыва. [Миграция](../migrations/001_initial.sql) хранит сессии, комнаты, события, квитанции, полное состояние матча и сроки автоматических действий. После рестарта API читает состояние из БД. [ADR 0003](adr/0003-command-transaction-and-player-view.md).

## Клиент и графика

[React](../apps/web/src/app.tsx) отображает меню, лобби и игру. Поле использует координаты, идентификатор слота и раскрытие из DTO. Ссылка-приглашение передаёт код комнаты в параметре `join`. В коде используются относительные ESM-импорты с расширением `.js` для TypeScript и type-only импорты типов протокола.

[Vite](../apps/web/vite.config.ts) проксирует `/api` и `/ws` при локальном запуске и собирает статику в `apps/web/dist`. В сборку графики входят только WebP из [реестра поставки](../data/asset-manifest.json) и [реестра производных для поля](../data/board-art-v2.json). Модуль `virtual:game-art` отдаёт URL по ID с версией на основе хеша. Вход и открытые камеры используют производные с проверенными кромками. Закрытые цели используют общий рисунок поставки. Происхождение графики описано в [ADR 0004](adr/0004-preserve-raster-sources.md) и [документе по графике](ALPHA_ASSETS.md).

[Runbook](ALPHA_RUNBOOK.md) описывает локальный запуск, изоляцию тестовой БД и границы закрытого доступа. [Приёмка](ALPHA_ACCEPTANCE.md) содержит фактические результаты Vitest, PostgreSQL, браузерных контекстов, сетевых замеров и проверки графики.
