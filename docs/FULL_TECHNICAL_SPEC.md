Для 3–4 игроков согласована возможность раунда без предателя. «Золото и предатели» использует собственный код, графику, тексты, состав карт по типам, подсчёт очков, порядок начала раунда, ботов и интерфейс.

Сохраняем утверждённые общие принципы: скрытые роли, поочерёдные ходы, карточные соединяемые туннели, обвалы, препятствия и ремонт оборудования, приватная разведка, поиск золота и социальная игра. 16 геометрий туннельных ассетов, 11 иллюстраций действий и остальные уже нарисованные элементы сохраняются как библиотека. **Количество изображений не определяет количество экземпляров колоды, условия победы или систему наград.**

## 1. Продукт и объём работ

Целевая игра — браузерный мультиплеер на русском языке для 3–10 участников, быстрый вход по ссылке или коду комнаты, гостевой профиль, один общий сервер. Вертикальный и горизонтальный телефон, компьютер. Для первой поставки: создание/вход в закрытую комнату, лобби, готовность, приватная роль, рука, поле, разрешённые действия, чат/журнал, восстановление после отключения, завершение раунда/матча, повтор, боты, инструкции запуска и тесты. UI должен быть настоящим интерактивным приложением, а не нарисованным экраном.

Готовность движка, закрытой альфы с профилем v1 и публичной версии проверяется отдельно. Публичный выпуск требует отдельного решения владельца, проверки прав и художественной приёмки. Telegram, MAX, VK, платежи, магазин, рекламные SDK, рейтинги, турниры, голосовой чат и платные преимущества находятся за рамками закрытой альфы.

## 2. Правила как данные, а не зашитый алгоритм конкретной игры

### 2.1 Модель
Движок принимает валидированный immutable `Ruleset` при создании матча: лимиты игроков, число раундов, состав общей колоды, раздача, назначение ролей, список целей/их координаты и свойства, правила ходов, ограничения оборудования, условия окончания и стратегия начисления наград. Матч хранит ID, версию и SHA-256 канонической сериализации профиля. Нельзя менять действующий профиль под уже начатым матчем. Серверные функции стратегий явно зарегистрированы и типизированы; не исполнять произвольный код из JSON и не предоставлять создание ruleset клиенту. Ошибка неизвестного ID, несогласованной геометрии, невозможной раздачи или недостающего обработчика обнаруживается при старте, а не в матче.

`data/card-catalog-v2.json` описывает 16 геометрий (7 соединённых и 9 тупиковых) и 11 действий. Компоненты N/E/S/W — группы реально связанных портов. Один тип арта может иметь несколько экземпляров; у каждого свой непрозрачный instanceId. Профиль отдельно задаёт количества. Не считать исходное количество физических карт, чужую систему наград или распределение ролей нормативным требованием. Для тестов можно менять конфигурации в fixture, не подменяя правила текущего матча. Нет требования реализовать чужой ruleset как совместимый режим.

### 2.2 «Путь к золоту» (v1)

Старатели прокладывают непрерывный путь от входа к одной золотой камере. Предатели мешают им. Каждый участник играет одну карту за ход.

| Параметр | Профиль внутреннего теста |
|---|---|
| Игроки | 3–10 |
| Раунды | 3 |
| Роли | При 3–4 игроках с вероятностью 20% все старатели, иначе один случайный предатель. При 5 игроках один предатель, при 6–8 два, при 9–10 три |
| Рука | 6 карт при 3–5 игроках, 5 при 6–7, 4 при 8–10 |
| Общая колода | 40 туннелей и 27 действий. Количества по типам заданы в JSON |
| Поле | Вход (0,0). Камеры (8,-2), (8,0) и (8,2). Между входом и центральной камерой семь свободных клеток |
| Цели | Одна золотая камера и две пустые. Сервер заново перемешивает их расположение каждый раунд |
| Победа старателей | Золотая камера впервые стала достижимой от входа |
| Победа предателей | Исчерпаны колода и все руки, золото не найдено, в раунде есть хотя бы один предатель |
| Раунд без победителя | Исчерпаны колода и все руки, золото не найдено, предателя в раунде не было |
| Лимит ходов | Без лимита на раунд. Ведущий может включить таймер отдельного хода |
| Награда | Личный числовой счёт по разделу 3.5 |

Профиль использует существующие иллюстрации. Все закрытые камеры имеют одну рубашку. Чтобы получить 27 действий, добавляется второй экземпляр карты ремонта кирки или фонаря. Остальные количества по типам сохраняются из v0.

## 3. Игровой движок: функциональный контракт

### 3.1 Раунд и состояние
Порядок мест фиксируется. В начале каждого раунда сервер проводит жеребьёвку отсутствия предателя для 3–4 мест, затем перемешивает роли, цели и колоду. Результат жеребьёвки скрыт до конца раунда. Предыдущая роль не влияет на новую. Сервер случайно выбирает первого стартующего, а каждый следующий раунд начинает следующее место по кругу после предыдущего стартующего. Счёт накапливается, поле, карты, поломки и разведка сбрасываются. Движок принимает источник случайности. Сервер использует безопасную случайность, тесты используют воспроизводимый источник.

Фазы: LOBBY → ROUND_SETUP → ROLE_REVEAL → TURN → ROUND_RESOLVED → REWARD_SETTLEMENT → ROUND_SUMMARY → следующий ROUND_SETUP либо MATCH_FINISHED; ABANDONED для истёкшего матча. Произвольные переходы запрещены. Подтверждение просмотра роли не меняет её и не публикует чужие сведения. Переход из ROLE_REVEAL после подтверждения всех или тайм-аута 20 секунд (проектная настройка). При завершении раунда блокируются игровые ходы до готовности следующего. RECONNECTING — клиентский индикатор, не сброс матча.

### 3.2 Граф и стыковка
Поле разреженное, x вправо, y вниз; тайл — координата, typeId, instanceId, rotation, компоненты. Вход неизменяем; открытые порты входа соединены между собой. Для обычных тайлов повороты 0° и 180° (N↔S, E↔W) без зеркалирования в игре. Координаты целые, |x|, |y| ≤128. Граф содержит вершины (tileInstanceId, componentIndex), ребро между соседними компонентами только при совпадающих портах. BFS/DFS от входа даёт достижимые компоненты. Не склеивать раздельные тупики и не считать визуальное касание ребром.

Для размещения: свободная незарезервированная клетка, экземпляр в руке, очередь игрока, допустимый поворот, ограничения оборудования; все ортогональные соседи должны совпасть порт-к-порту или стена-к-стене. Хотя бы один компонент новой карты соединён с входом после гипотетического размещения. Диагональ не соединяет. Отрезанная ветка остаётся лежать, но строить только от неё нельзя до восстановления связи. Удаление/добавление всегда пересчитывает граф. Раздельные тупики N/E/S/W не являются перекрёстком. Предпросмотр чистый, не изменяет исходный state.

### 3.3 Камеры
Все три клетки зарезервированы. У камеры один публичный западный вход, одинаковый для золота и пустой породы. Камера завершает ветку тоннеля. Стыковка зависит от открытых сведений о портах. Когда непрерывный путь от входа доходит до камеры, её содержимое становится общим. Пустая камера сохраняет положение и раскрытие до конца раунда, даже если путь после обвала пропал. После каждого изменения поля сервер заново проверяет доступность камер. Приватная разведка даёт возможность узнать содержимое, сохраняя публичную рубашку. Для всех камер используются непрозрачные ID.

### 3.4 Ход и действия
Действовать может только активное место. Выбор в UI не расходует карту. Подтверждённая валидная команда расходует ровно один экземпляр:
- PLAY_TUNNEL: по правилам графа; при любой неисправности строительство недоступно.
- PLAY_BREAK: один инструмент другого игрока; нельзя ломать уже сломанный, себя; карта становится видимым статусом.
- PLAY_REPAIR: свой/чужой соответствующий статус; снимает ровно один, ремонт и снятая поломка уходят в сброс. Для пары выбрать один инструмент из двух; не ремонтировать впрок.
- PLAY_COLLAPSE: удалить обычный туннель, не вход/цель. Карты уходят в сброс; пересчитать достижимость. Отрезанные карты не исчезают. Удалённую клетку можно занять снова.
- PLAY_SCOUT: узнать содержание одной ещё закрытой камеры приватно; публично только факт действия. Не раскрывать цель публично, не изменять карту. Повтор разрешён пока закрыта.
- DISCARD: закрытый сброс одного экземпляра, без эффекта. Игрок с повреждениями сохраняет право применять действия и сбрасывать.

После принятого хода увеличить счётчик и обновить достижимость камер. Проверка победы старателей имеет приоритет, даже если сыграна последняя карта или путь завершил предатель. Если раунд продолжается, участник добирает одну карту из колоды. Когда колода пуста, сброс не перемешивается и участники доигрывают руки. Места без карт пропускаются без расхода хода. Если колода и руки пусты, сервер определяет исход по наличию предателя. Невалидная команда не меняет ревизию, руку, счётчик или RNG. Таймер хода по умолчанию выключен. При включённом таймере сервер закрыто сбрасывает первую карту активного места в стабильном порядке, используя общую проверку команд.

### 3.5 Награды
Победа старателей приносит каждому старателю +2 очка. Если путь завершил старатель, он получает ещё +1. Победа предателей приносит каждому предателю +2. Проигравшие и участники раунда без победителя получают 0. Очки начисляются автоматически и атомарно, повтор команды не дублирует начисление. В итогах раунда раскрываются роли и все камеры, начисление и текущая сумма видны только самому игроку. После трёх раундов сумма становится общей. Побеждают все участники с наибольшим положительным счётом. Если у всех ноль, матч заканчивается без победителя. Повтор создаёт матч с новым ID, нулевым счётом и новым источником случайности.

### 3.6 API чистого core
`validateCatalog`, `validateRuleset`, `newMatch`, `startRound`, `rotatePorts`, `buildGraph`, `reachableComponents`, `legalMoves`, `applyCommand`, `evaluateOutcome`, `settleRewards`, `publicView`, `playerView`, `assertInvariants`. Результат — новый state и события либо типизированная доменная ошибка. Core не зависит от DOM, времени, сети, БД. Все переходы воспроизводимы тестами. Не импортировать чужую реализацию.

## 5. Сущности и долговременное состояние

| Сущность | Данные |
|---|---|
| Profile / GuestSession | внутренний userId, имя, avatarId; хеш высокоэнтропийного токена, срок/отзыв |
| Room / Seat | roomId, joinCode, hostId, места, готовность, presence, статус/срок, настройки |
| Match | immutable seats, rulesetId/version/digest, roundNo, phase, revision |
| RoundState | серверные роли, тайные цели, порядок колоды, руки, сброс, тайлы/граф, статусы, очередь, счётчик ходов, разведка |
| RewardLedger | private score, атомарные начисления с уникальным ключом match/round/seat |
| MatchEvent / CommandReceipt | sequence, revision, actor, eventType, public/private projection; commandId, digest, результат |
| ChatMessage | roomId, messageId, authorSeat, текст, время и метаданные модерации |

PostgreSQL, миграции и индексы. Снимок JSONB с schemaVersion + журнал; обновление state, события и receipt в одной транзакции (row lock/CAS). Уникальность (matchId, actorId, commandId). Перезапуск восстанавливает снимок, сроки и последнюю ревизию, а не пересоздаёт роль. Presence и чат имеют отдельную последовательность, не меняют игровую revision. Срок закрытой комнаты и сессий документировать; предложено: лобби 24 ч, завершённый матч 7 дней, гостевая сессия 30 дней; ручное удаление тестовых данных. Не логировать секреты.

## 6. Сетевой протокол и защита

HTTP: POST /api/session/guest, GET /api/session, POST /api/rooms, POST /api/rooms/join, GET /api/rooms/:roomId, POST /api/rooms/:roomId/leave, health/live и health/ready. WebSocket /ws — проверка сессии, origin и членства; subscribe/resync/command/ack/event. Допускается HTTP transport команд только с тем же reducer. Автор берётся из сессии, не из присланного playerId. Игровая команда: commandId, roomId, matchId, expectedRevision + discriminated union:
PLAY_TUNNEL(instanceId,x,y,rotation); PLAY_BREAK(instanceId,targetSeatId); PLAY_REPAIR(instanceId,targetSeatId,tool); PLAY_COLLAPSE(instanceId,x,y); PLAY_SCOUT(instanceId,goalSlotId); DISCARD(instanceId). Ready/start/summary подтверждения — отдельные команды фаз. Сервер начисляет награды автоматически.

Проверять одинаковый commandId/digest прежде stale revision: повтор возвращает прежний безопасный ack; тот же ID с другим payload — ошибка. Новая команда выполняется атомарно только на текущей revision. После commit публикуется отфильтрованное событие; при разрыве sequence — безопасный snapshot. Стабильные коды NOT_MEMBER, NOT_YOUR_TURN, STALE_REVISION, CARD_NOT_IN_HAND, ILLEGAL_PLACEMENT, INVALID_TARGET, TOOL_BROKEN, WRONG_PHASE, COMMAND_ID_REUSED, ROOM_FULL и т.д. Ошибка не выдаёт скрытое содержимое; UI сохраняет разумный выбор, не переотправляет другой ход сам.

**Публично** доступны места, аватары, ready/presence, раунд, номер хода, условия победы, поле, открытые камеры, рубашки, статусы, количества карт, журнал и исход раунда. Роли становятся общими после раунда. **Только игроку** доступны его роль, рука, разведка, начисления и текущая сумма. **Только серверу** доступны фактическое число предателей до конца раунда, чужие руки, скрытые лица целей, порядок колоды, закрытый сброс, RNG/seed и полный state. Сервер формирует PublicView и PlayerView, исключая передачу скрытых данных через HTML, preload, URL, ошибки, логи, аналитику, localStorage, SSR, service worker и debug endpoint. Команды разведки используют непрозрачный slotId.

Гость: случайный токен в HttpOnly/SameSite cookie, Secure для HTTPS, хеш в БД, CSRF/origin, проверки membership. Ограничения кодов приглашения, rate limit входа/чат/команд, schema и длины payload, нормализация имён/текста, безопасный рендер без HTML, CSP; только серверный TLS при внешнем тесте, БД не открывать наружу. Без обязательного email/телефона. После обновления/разрыва возвращать то же место, роль, руку и ревизию. Не присваивать чужое место; выход во время матча не стирает state. Ведущий может управлять лобби до старта; перенос host при уходе в лобби по стабильному порядку. Запрет новых мест после начала; восстановление владельца места по сессии. Не допускать вечного ожидания: в закрытом тесте ведущий может заранее включить таймер и ботов; при отключении без таймера матч ожидает, явно показывает отсутствие игрока и даёт завершить комнату, без раскрытия роли. 

## 7. Интерфейс и сценарии

Язык русский, строки из словаря, технические ID стабильны, интерактивные элементы имеют aria-label, клавиатурный фокус, touch-зоны ~44 px; соблюдать safe area, reduced motion, контраст, не только цвет. Стиль — насыщенная рисованная шахта, сине-фиолетовая порода, янтарные фонари, золотые акценты, выразительные карты; никакой сепии, фотостиля, административной панели, SVG-арта. Сохранить существующие референсы и логотип; не превращать их в скриншоты с невидимыми кнопками.

| Экран | Сценарий и приёмка |
|---|---|
| Меню | Логотип, имя гостя, создать/войти, правила, звук |
| Комната | Код/ссылка, 3–10 мест, готовность, ведущий, таймер и боты в тесте, профиль v1 |
| Роль | Только собственная карта и цель, подтверждение, повторный приватный просмотр |

| Размещение | Выбор карты, разрешённые клетки, ghost, 180°, отмена/подтвердить, ожидание ack |

| Правила | Самостоятельный текст из текущего профиля; не импортировать чужой rulebook |

Телефон 360×800, 390×844 и landscape: компактная верхняя строка, прокручиваемые аватары, максимально большая панорамируемая шахта, масштаб двумя пальцами и кнопками, рука снизу, выбор не перекрывает критическую область. Десктоп 1920×1080 и меньшие окна: центральная шахта, участники/чат сбоку, рука снизу. Управление мышью/тачем/клавиатурой; фокус на входе, цели, последнем ходе. Не требовать drag-and-drop. Все пользователи видят тот же roomId и revision. Чат комнаты без тайного командного канала, история по messageId, длина 300 символов и антифлуд; обсуждения и блеф допустимы, не подтверждать слова игрока тайным состоянием. Журнал отделён от чата, текст из публичных событий; закрытый сброс/разведка не раскрываются.

## 8. Графика, фактический статус и QA

В последнем локальном архиве владельца: 40 уникальных карточных иллюстраций (16 туннелей, 11 действий, 5 вход/цели, 2 роли, 3 награды, 3 рубашки), 80 WebP в двух разрешениях, 24 отдельных растровых иконки, логотип, 2 кандидатных фона, исходники и референсы. **На GitHub main в момент составления v2 ещё более ранняя поставка: 35 типов/70 WebP и SVG. PR с импортом 16 туннелей ранее не подтверждал публикацию самих файлов. Этот PR меняет документы/JSON, не загружает изображения.** Если работа идёт на локальном компьютере владельца, использовать последнюю распакованную поставку; если checkout GitHub — составить точный missing-assets список и использовать последний локальный пакет при наличии. Не выдумывать наличие путей. Отсутствие арта не блокирует E1–E2, но блокирует художественную сдачу E4.

Размер всех карточек 512×768, компактных 256×384, исходники 1024×1536. Без встроенных названий/чисел/описаний. На поле 2:3, без промежутков, скруглений, обводок и декора поперёк проходов; центры N/S x=256/128, E/W y=384/192, ширина 160/80 px, допустимое отклонение границы до 2 px. Граф определяется метаданными, не цветом пикселя. Проверить 16 геометрий при обоих поворотах и разрешениях, раздельность тупиков, скриншоты реально собранных полей при DPR 1/2/3. Тесты стыков не заменяют художественную приёмку.

Открытые задачи: вход — 4 связанных порта, раскрытая камера v0 — только W, камень и золото одинаково стыкуются; закрытые цели одинаковы. Нормализовать эти иллюстрации, проверять не меняя правила из-за картинки. Парный ремонт читается как выбор одного; поломка фонаря не похожа на работающий; награды 1/2/3 различимы; нейтральные публичные аватары (4–10), фоны, app-icon 192/512, social-cover и материалы панелей — отдельно принять. Сохранять исходники, не пересоздавать принятый арт без необходимости. Иконки из нового прозрачного растрового набора, логотип WebP; не использовать старые SVG, не включать SVG, archive, source PNG и макеты в web dist. CSS для текста, кнопок, сетки, подсветок, состояний и анимаций — не замена арта. При каждом экспорте реестр: ID/путь/формат/размер/байты/SHA-256/происхождение/статус QA; компактная карта целевой бюджет ≤45 КиБ, стандартная ≤120 КиБ, исключения обосновать качеством. Программные fixture только в тестовой сборке, явное обозначение.

## 9. Боты и воспроизводимость

В закрытом режиме ведущий может добавить обозначенных ботов до 3–10 мест. Бот получает PlayerView, допустимые ходы и публичные данные о каталоге и геометрии. Из тайных данных ему доступны собственная роль, рука и разведка. Бот-старатель оценивает выходы достижимых компонентов, продвигается к возможному золоту и ремонтирует инструменты. Бот-предатель оценивает разрыв пути обвалом, блокировку строительства и закрытие полезных выходов. Боты и таймер отправляют общие валидируемые команды. Тесты фиксируют руки, роли и seed только в изолированном окружении.

## 10. Тестирование и критерии

| ID | Проверка |
|---|---|
| R01 | Проверка каталога и профилей, уникальности ID и количества 67 в v1 |
| R02 | Рука 6/5/4 для N=3…10, жеребьёвка 20% при 3–4, обычные роли при 5–10, очистка статусов |
| R03 | Повороты 0/180 и 16 геометрий; 90° запрещён |
| R04 | Все занятые соседи, стена/порт; диагональ не соединяется |
| R05 | Изолированные компоненты N/E/S/W; доступный компонент не делает доступной всю карту |
| R06 | Отсоединённая ветка не позволяет строить; восстановление графа после обхода |
| R07 | Камеры принимают только западный порт. Лицо не меняет допустимость ходов |
| R08 | Пустая камера раскрывается, сохраняет положение и остаётся раскрытой после потери пути |
| R09 | Подключение золота завершает раунд, включая путь предателя и последний экземпляр |
| R10 | Поломки, запрет дубликата/самосаботажа, блок строительства |
| R11 | Ремонт только существующей одной поломки, пара выбирает одну; действия и сброс доступны при поломках |
| R12 | Обвал не удаляет старт/цель, клетка снова пригодна для строительства |
| R13 | Разведка приватна, закрытая цель не раскрывается другим |
| R14 | Закрытый сброс, ходы после прежнего лимита, доигрывание рук и пропуск пустых мест, исход при исчерпании с предателем и без него |
| R15 | По +2 победителям и +1 старателю за завершение пути, 0 проигравшим и всем при отсутствии победителя, защита от повторного начисления |

| R17 | Невалидная команда не мутирует состояние/счётчик/RNG; тесты инвариантов, property-based граф |
| R18 | Другой валидный fixture с иным числом раундов/экземпляров/целей работает без изменения core; заморозка профиля в матче |

| A01–A02 | Проверить реально доступный манифест/хеши и новые ассеты; отсутствие SVG/архивов в dist; скриншоты фактического поля и семантика арта |

Симулятор: целевой прогон 100 завершённых матчей каждого размера 3–10 (800), зафиксированные seeds, ноль необработанных исключений, зависаний и нарушений инвариантов. Победные доли и время — измерения для будущего решения владельца, не гарантия баланса. Интеграционные тесты на отдельной тестовой БД, не удалять production. Логи, версия, команды и скриншоты в отчёте, провал — воспроизводимый тест.

## 11. Производительность и эксплуатация

Цели альфы (не измеренные обещания): начальная загрузка ≤1,5 МБ и интерактивность ≤3 с при 10 Мбит/с/RTT100 мс; lazy load WebP, cache публичного арта; 20 комнат по 10 участников, p95 обработки команды ≤150 мс без сети, p95 подтверждения UI ≤500 мс при RTT100 мс; пан/зум стремится к 60 fps, без полного re-render из-за чата/presence. Измерять на описанном стенде; исправлять узкие места, не вводить дорогую инфраструктуру по умолчанию. Health checks, структурированные логи без секретов, метрики rooms/WS/latency/reconnect, graceful shutdown, backup/restore, миграции, runbook. LAN-тест и HTTPS для внешнего закрытого теста; не публиковать БД/токены.

## 12. Реальные тесты и согласование правил

Закрытые партии 3, 5–6, 10 мест; допускаются обозначенные боты, отдельно хотя бы одна партия людей. iPhone Safari, Android Chromium, desktop Chromium/Firefox при наличии; эмуляцию не называть реальным устройством. Поворот, смена вкладки, обрыв 10–30 с и рестарт. Фиксировать завершённость, длительность, повторные партии, успешные приглашения, недоступные ходы, читаемость и причины выхода. Не собирать тайные сведения/чат во внешнюю аналитику. Изменения профиля только отдельной версией с обоснованием и тестами. Вопросы коммерческого профиля — документ RULES_DECISIONS; не выдавать эксперимент за утверждённый баланс.

## 14. Определение готовности

Готовая внутренняя альфа запускается с чистого checkout, использует профиль v1 для новых матчей и открывает сохранённые матчи по их закреплённым профилям. Она завершает все фазы, выдерживает повтор команды и переподключение и хранит тайные данные на сервере. Проверки ассетов, игровых сценариев и браузеров фиксируются с результатами и ограничениями. Для публичного выпуска требуется отдельное решение о правилах, названии, правах на материалы и условиях обработки данных.

## 15. Платформы после браузерной приёмки

Один движок, один сервер и внутренний userId. Позднее проверить актуальные SDK и правила Telegram Mini Apps, MAX, VK Mini Apps; отдельные адаптеры identity, server-side verification, share/invite, deep link, capabilities. Возможность общей комнаты — архитектурная цель, не гарантия правил платформ. Монетизация отдельно: косметика/удобство, реклама между партиями, никаких платных игровых преимуществ. Не включать платформенные SDK сейчас.
