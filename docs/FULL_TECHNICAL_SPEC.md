**Статус:** задание на разработку универсального движка и закрытой браузерной альфы. Не лицензия, не заключение о правах, не утверждённые правила коммерческого релиза.

## 0. Приоритет документов и решение о смене подхода

Это ТЗ заменяет локальную редакцию 1.0 от 26.11.2026, которая требовала точного цифрового воспроизведения конкретной настольной игры, и прежние краткие спецификации в репозитории. Цель проекта — самостоятельная игра «Золото и предатели» с собственным кодом, графикой, персонажами, текстами и игровыми решениями. Не ставить задачу точного воспроизведения конкретного чужого издания, не переносить его полный набор правил, охраняемые материалы или программный код. Не скрывать за другим названием прежнюю задачу.

Сохраняем утверждённые общие принципы: скрытые роли, поочерёдные ходы, карточные соединяемые туннели, обвалы, препятствия и ремонт оборудования, приватная разведка, поиск золота и социальная игра. 16 геометрий туннельных ассетов, 11 иллюстраций действий и остальные уже нарисованные элементы сохраняются как библиотека. **Количество изображений не определяет количество экземпляров колоды, условия победы или систему наград.**

Единственные активные источники для реализации:
- `docs/FULL_TECHNICAL_SPEC.md` (этот документ);
- `AGENTS.md`;
- `data/card-catalog-v2.json` — геометрии и примитивы действий, без количества экземпляров;
- `data/game-config.json` — указатель на профиль;
- `data/rulesets/playtest-expedition-v0.json` — экспериментальные правила закрытой разработки;
- `data/asset-manifest.json` — инвентаризация фактически присутствующего арта, не правила.

Старый `data/cards.json`, документы с датой 08–09.11, `archive/` и макеты — исторические материалы, не runtime. Не подгружать автоматически прежний состав или конфигурацию из локального ZIP v1.0. При конфликте использовать v2.0. Не объявлять параметры экспериментального режима утверждёнными владельцем. Спорные продуктовые решения записывать в `docs/RULES_DECISIONS.md`; не блокировать независимые E0–E5, если можно продолжить работу по этому профилю или протестировать отдельный примитив.

## 1. Продукт и объём работ

Целевая игра — браузерный мультиплеер на русском языке для 3–10 участников, быстрый вход по ссылке или коду комнаты, гостевой профиль, один общий сервер. Вертикальный и горизонтальный телефон, компьютер. Для первой поставки: создание/вход в закрытую комнату, лобби, готовность, приватная роль, рука, поле, разрешённые действия, чат/журнал, восстановление после отключения, завершение раунда/матча, повтор, боты, инструкции запуска и тесты. UI должен быть настоящим интерактивным приложением, а не нарисованным экраном.

Разделяем готовность: **универсальный движок** (не привязан к одному профилю), **играбельная внутренняя альфа** (экспериментальный профиль v0), **публичная версия** (отдельно утверждённый самостоятельный ruleset, юридическая и художественная приёмка). Публикацию и платный запуск не проводить. Не реализовывать Telegram/MAX/VK, платежи, магазин, рекламные SDK, рейтинги, турниры, голосовой чат и платные преимущества сейчас. Не добавлять Vibe целиком, Base44, fal или платные внешние сервисы без согласования.

## 2. Правила как данные, а не зашитый алгоритм конкретной игры

### 2.1 Модель
Движок принимает валидированный immutable `Ruleset` при создании матча: лимиты игроков, число раундов, состав общей колоды, раздача, назначение ролей, список целей/их координаты и свойства, правила ходов, ограничения оборудования, условия окончания и стратегия начисления наград. Матч хранит ID, версию и SHA-256 канонической сериализации профиля. Нельзя менять действующий профиль под уже начатым матчем. Серверные функции стратегий явно зарегистрированы и типизированы; не исполнять произвольный код из JSON и не предоставлять создание ruleset клиенту. Ошибка неизвестного ID, несогласованной геометрии, невозможной раздачи или недостающего обработчика обнаруживается при старте, а не в матче.

`data/card-catalog-v2.json` описывает 16 геометрий (7 соединённых и 9 тупиковых) и 11 действий. Компоненты N/E/S/W — группы реально связанных портов. Один тип арта может иметь несколько экземпляров; у каждого свой непрозрачный instanceId. Профиль отдельно задаёт количества. Не считать исходное количество физических карт, чужую систему наград или распределение ролей нормативным требованием. Для тестов можно менять конфигурации в fixture, не подменяя правила текущего матча. Нет требования реализовать чужой ruleset как совместимый режим.

### 2.2 Экспериментальный режим «Две жилы» (v0)
Предлагаемый **самостоятельный профиль для закрытых тестов**, не финальное решение владельца. Смысл: бригада должна обнаружить и одновременно соединить со входом две золотые жилы; обнаружение одной не завершает раунд. Предатели мешают сохранить обе связи. После обнаружения жила остаётся известной, но обвал может отрезать её; доступность пересчитывается. Это меняет цель и тактику, а не просто названия карт. Сохранить привычную простоту: одна карта за ход, нет инвентаря ресурсов, одновременных смен или сложного симулятора.

| Параметр | Профиль внутреннего теста |
|---|---|
| Игроки | 3–10 |
| Раунды | 3 |
| Роли | 1 предатель при 3–5, 2 при 6–8, 3 при 9–10; остальные старатели |
| Рука | 5 карт при 3–8, 4 при 9–10 |
| Общая колода | 40 туннелей + 26 действий = 66 экземпляров, точные количества в JSON |
| Поле | Вход (0,0); три камеры (6,-2), (6,0), (6,2) |
| Цели | 2 жилы, 1 пустая камера, перемешаны сервером |
| Победа старателей | Обе жилы одновременно достижимы от входа |
| Победа предателей | Истёк лимит ходов либо исчерпаны карты без достижения цели |
| Лимит ходов | 6 × количество мест + 6 на раунд |
| Награда | Личный числовой счёт; правила ниже |

Профиль использует существующую иллюстрацию золота для обеих жил; из двух рисунков пустой камеры сервер выбирает один для пустого места. Все три закрытые карты имеют одну рубашку. Никакой новой картинки ради временного баланса. Конфигурация доступна только в локальной/закрытой альфе. Окончательную структуру целей, состав, баланс ролей, условия победы и очки владелец согласует после тестов; не обещать, что выбранные числа уже сбалансированы.

## 3. Игровой движок: функциональный контракт

### 3.1 Раунд и состояние
Фиксировать порядок мест; сервер независимо перемешивает роли, цели и разыгрываемые экземпляры. В профиле v0 число предателей гарантировано (см. JSON), не хранить лишнюю роль. Роли перераздаются каждый раунд. Первый стартующий игрок — серверная случайная жеребьёвка; в следующем раунде — следующее место относительно предыдущего стартующего. Личная сумма остаётся между раундами, поле, карты, статусы и разведка обнуляются. RNG внедряется в core; production использует безопасную серверную случайность, deterministic seed только в тестах.

Фазы: LOBBY → ROUND_SETUP → ROLE_REVEAL → TURN → ROUND_RESOLVED → REWARD_SETTLEMENT → ROUND_SUMMARY → следующий ROUND_SETUP либо MATCH_FINISHED; ABANDONED для истёкшего матча. Произвольные переходы запрещены. Подтверждение просмотра роли не меняет её и не публикует чужие сведения. Переход из ROLE_REVEAL после подтверждения всех или тайм-аута 20 секунд (проектная настройка). При завершении раунда блокируются игровые ходы до готовности следующего. RECONNECTING — клиентский индикатор, не сброс матча.

### 3.2 Граф и стыковка
Поле разреженное, x вправо, y вниз; тайл — координата, typeId, instanceId, rotation, компоненты. Вход неизменяем; открытые порты входа соединены между собой. Для обычных тайлов повороты 0° и 180° (N↔S, E↔W) без зеркалирования в игре. Координаты целые, |x|, |y| ≤128. Граф содержит вершины (tileInstanceId, componentIndex), ребро между соседними компонентами только при совпадающих портах. BFS/DFS от входа даёт достижимые компоненты. Не склеивать раздельные тупики и не считать визуальное касание ребром.

Для размещения: свободная незарезервированная клетка, экземпляр в руке, очередь игрока, допустимый поворот, ограничения оборудования; все ортогональные соседи должны совпасть порт-к-порту или стена-к-стене. Хотя бы один компонент новой карты соединён с входом после гипотетического размещения. Диагональ не соединяет. Отрезанная ветка остаётся лежать, но строить только от неё нельзя до восстановления связи. Удаление/добавление всегда пересчитывает граф. Раздельные тупики N/E/S/W не являются перекрёстком. Предпросмотр чистый, не изменяет исходный state.

### 3.3 Камеры профиля v0
Все три позиции зарезервированы. **У каждой камеры публичный фиксированный вход W**, независимо от её тайного содержимого. Остальные стороны закрыты; камера — терминальная вершина, не сквозной туннель. Обычные карты обязаны совпасть с этим известным портом, без исключений при раскрытии. Закрытая камера не участвует в транзитном пути; если достижимый путь подходит к W, раскрыть содержимое публично и сохранить раскрытие до конца раунда. Никаких проверок хода с использованием тайного лица. У двух золотых камер разные opaque slotId, одна иллюстрация; одна пустая. Сканировать после изменения графа все три камеры, определить достижимость заново; ранее раскрытые камеры не закрываются после обвала. Победа при двух одновременно достижимых жилах. Арт старта и всех открытых камер подлежит QA по этой НОВОЙ геометрии: старые логические порты целей из ТЗ 1.0 больше не действуют. В закрытом dev возможны явно отмеченные вспомогательные наложения/fixture; финальный арт не подменять схематичным рисунком.

### 3.4 Ход и действия
Действовать может только активное место. Выбор в UI не расходует карту. Подтверждённая валидная команда расходует ровно один экземпляр:
- PLAY_TUNNEL: по правилам графа; при любой неисправности строительство недоступно.
- PLAY_BREAK: один инструмент другого игрока; нельзя ломать уже сломанный, себя; карта становится видимым статусом.
- PLAY_REPAIR: свой/чужой соответствующий статус; снимает ровно один, ремонт и снятая поломка уходят в сброс. Для пары выбрать один инструмент из двух; не ремонтировать впрок.
- PLAY_COLLAPSE: удалить обычный туннель, не вход/цель. Карты уходят в сброс; пересчитать достижимость. Отрезанные карты не исчезают. Удалённую клетку можно занять снова.
- PLAY_SCOUT: узнать содержание одной ещё закрытой камеры приватно; публично только факт действия. Не раскрывать цель публично, не изменять карту. Повтор разрешён пока закрыта.
- DISCARD: закрытый сброс одного экземпляра, без эффекта. Игрок с повреждениями сохраняет право применять действия и сбрасывать.

После валидного хода увеличить счётчик хода, пересчитать достижимость/раскрытие, проверить победу старателей первой. Если нет победы и исчерпан лимит — выигрыш предателей. Иначе добрать одну карту, пока колода не пуста, не перемешивать сброс; если колода и все руки пусты, выигрывают предатели. Пропускать места с пустыми руками при исчерпанной колоде, не расходуя ход. В профиле v0 не бывает пустой руки при непустой колоде вне атомарного reducer; если инвариант нарушен — техническая ошибка, а не бесконечная очередь. Невалидный ход не меняет revision, руки, счётчик или RNG. Таймер хода по умолчанию выключен; при включённом таймере сервер вызывает обычную команду сброса первого экземпляра в стабильном порядке, не раскрывает его тип и соблюдает те же проверки.

### 3.5 Награды профиля v0
Нет физической стопки наград и последовательного выбора из общей руки. При успехе бригады всем старателям +2, старателю, чьим ходом обе жилы стали одновременно доступными, дополнительно +1. Если последним был предатель, бонус никому. При успехе предателей каждому из них +1 за раунд и +1 за каждую недостающую из двух одновременно достижимых жил (при поражении бригады возможны 2 или 3 очка). Проигравшая сторона — 0. Результат, роли и открытые камеры можно раскрыть после раунда; не публиковать скрытые лица неразведанных камер до завершения раунда, затем допустимо раскрыть все. Личные начисления и накопленный счёт доступны только владельцу до финала. UI использует рисунки 1/2/3 золота как оформление, а не как ограниченный запас. Выдача атомарна и идемпотентна. После трёх раундов открываются личные суммы; максимум — победитель, ничья допускается. Повтор — новый matchId, новый счёт и seed. Это новый экспериментальный режим; не переносить старую систему драфта наград.

### 3.6 API чистого core
`validateCatalog`, `validateRuleset`, `newMatch`, `startRound`, `rotatePorts`, `buildGraph`, `reachableComponents`, `legalMoves`, `applyCommand`, `evaluateOutcome`, `settleRewards`, `publicView`, `playerView`, `assertInvariants`. Результат — новый state и события либо типизированная доменная ошибка. Core не зависит от DOM, времени, сети, БД. Все переходы воспроизводимы тестами. Не импортировать чужую реализацию.

## 5. Сущности и долговременное состояние

| Сущность | Данные |
|---|---|
| Profile / GuestSession | внутренний userId, имя, avatarId; хеш высокоэнтропийного токена, срок/отзыв |
| Room / Seat | roomId, joinCode, hostId, места, готовность, presence, статус/срок, настройки |
| Match | immutable seats, rulesetId/version/digest, roundNo, phase, revision |
| RoundState | серверные роли, тайные цели, порядок колоды, руки, сброс, тайлы/граф, статусы, очередь, счётчик ходов, разведка |
| RewardLedger | private score, атомарные начисления с уникальным ключом match/round/seat |
| MatchEvent / CommandReceipt | sequence, revision, actor, eventType, public/private projection; commandId, digest, результат |
| ChatMessage | roomId, messageId, authorSeat, текст, время и метаданные модерации |

PostgreSQL, миграции и индексы. Снимок JSONB с schemaVersion + журнал; обновление state, события и receipt в одной транзакции (row lock/CAS). Уникальность (matchId, actorId, commandId). Перезапуск восстанавливает снимок, сроки и последнюю ревизию, а не пересоздаёт роль. Presence и чат имеют отдельную последовательность, не меняют игровую revision. Срок закрытой комнаты и сессий документировать; предложено: лобби 24 ч, завершённый матч 7 дней, гостевая сессия 30 дней; ручное удаление тестовых данных. Не логировать секреты.

## 6. Сетевой протокол и защита

HTTP: POST /api/session/guest, GET /api/session, POST /api/rooms, POST /api/rooms/join, GET /api/rooms/:roomId, POST /api/rooms/:roomId/leave, health/live и health/ready. WebSocket /ws — проверка сессии, origin и членства; subscribe/resync/command/ack/event. Допускается HTTP transport команд только с тем же reducer. Автор берётся из сессии, не из присланного playerId. Игровая команда: commandId, roomId, matchId, expectedRevision + discriminated union:
PLAY_TUNNEL(instanceId,x,y,rotation); PLAY_BREAK(instanceId,targetSeatId); PLAY_REPAIR(instanceId,targetSeatId,tool); PLAY_COLLAPSE(instanceId,x,y); PLAY_SCOUT(instanceId,goalSlotId); DISCARD(instanceId). Ready/start/summary подтверждения — отдельные команды фаз. Награды v0 автоматические, клиент не начисляет их.

Проверять одинаковый commandId/digest прежде stale revision: повтор возвращает прежний безопасный ack; тот же ID с другим payload — ошибка. Новая команда выполняется атомарно только на текущей revision. После commit публикуется отфильтрованное событие; при разрыве sequence — безопасный snapshot. Стабильные коды NOT_MEMBER, NOT_YOUR_TURN, STALE_REVISION, CARD_NOT_IN_HAND, ILLEGAL_PLACEMENT, INVALID_TARGET, TOOL_BROKEN, WRONG_PHASE, COMMAND_ID_REUSED, ROOM_FULL и т.д. Ошибка не выдаёт скрытое содержимое; UI сохраняет разумный выбор, не переотправляет другой ход сам.

**Публично:** места, нейтральные аватары, ready/presence, раунд, ход, лимит ходов, поле, открытые камеры, одинаковые закрытые рубашки, публичные статусы, количества карт, журнал, исход раунда, раскрытые после раунда роли. **Только владельцу:** своя роль, экземпляры руки, разведка, начисления/сумма; до финала не показывать чужой счёт. **Только серверу:** чужие руки, скрытые лица и их привязки, порядок колоды, закрытый сброс, RNG/seed и полный state. Public/Player DTO создаёт сервер; не передавать полный state с CSS-фильтрацией. Не выдавать скрытые данные через preload, URL, ошибки, логи, analytics, localStorage, SSR, service-worker или debug endpoint. Opaque slotId для цели, не название лица. Для legalMoves использовать только доступные публичные сведения и собственную руку.

Гость: случайный токен в HttpOnly/SameSite cookie, Secure для HTTPS, хеш в БД, CSRF/origin, проверки membership. Ограничения кодов приглашения, rate limit входа/чат/команд, schema и длины payload, нормализация имён/текста, безопасный рендер без HTML, CSP; только серверный TLS при внешнем тесте, БД не открывать наружу. Без обязательного email/телефона. После обновления/разрыва возвращать то же место, роль, руку и ревизию. Не присваивать чужое место; выход во время матча не стирает state. Ведущий может управлять лобби до старта; перенос host при уходе в лобби по стабильному порядку. Запрет новых мест после начала; восстановление владельца места по сессии. Не допускать вечного ожидания: в закрытом тесте ведущий может заранее включить таймер и ботов; при отключении без таймера матч ожидает, явно показывает отсутствие игрока и даёт завершить комнату, без раскрытия роли.

## 8. Графика, фактический статус и QA

В последнем локальном архиве владельца: 40 уникальных карточных иллюстраций (16 туннелей, 11 действий, 5 вход/цели, 2 роли, 3 награды, 3 рубашки), 80 WebP в двух разрешениях, 24 отдельных растровых иконки, логотип, 2 кандидатных фона, исходники и референсы. **На GitHub main в момент составления v2 ещё более ранняя поставка: 35 типов/70 WebP и SVG. PR с импортом 16 туннелей ранее не подтверждал публикацию самих файлов. Этот PR меняет документы/JSON, не загружает изображения.** Если работа идёт на локальном компьютере владельца, использовать последнюю распакованную поставку; если checkout GitHub — составить точный missing-assets список и использовать последний локальный пакет при наличии. Не выдумывать наличие путей. Отсутствие арта не блокирует E1–E2, но блокирует художественную сдачу E4.

Размер всех карточек 512×768, компактных 256×384, исходники 1024×1536. Без встроенных названий/чисел/описаний. На поле 2:3, без промежутков, скруглений, обводок и декора поперёк проходов; центры N/S x=256/128, E/W y=384/192, ширина 160/80 px, допустимое отклонение границы до 2 px. Граф определяется метаданными, не цветом пикселя. Проверить 16 геометрий при обоих поворотах и разрешениях, раздельность тупиков, скриншоты реально собранных полей при DPR 1/2/3. Тесты стыков не заменяют художественную приёмку.

Открытые задачи: вход — 4 связанных порта, раскрытая камера v0 — только W, камень и золото одинаково стыкуются; закрытые цели одинаковы. Нормализовать эти иллюстрации, проверять не меняя правила из-за картинки. Парный ремонт читается как выбор одного; поломка фонаря не похожа на работающий; награды 1/2/3 различимы; нейтральные публичные аватары (4–10), фоны, app-icon 192/512, social-cover и материалы панелей — отдельно принять. Сохранять исходники, не пересоздавать принятый арт без необходимости. Иконки из нового прозрачного растрового набора, логотип WebP; не использовать старые SVG, не включать SVG, archive, source PNG и макеты в web dist. CSS для текста, кнопок, сетки, подсветок, состояний и анимаций — не замена арта. При каждом экспорте реестр: ID/путь/формат/размер/байты/SHA-256/происхождение/статус QA; компактная карта целевой бюджет ≤45 КиБ, стандартная ≤120 КиБ, исключения обосновать качеством. Программные fixture только в тестовой сборке, явное обозначение.

## 9. Боты и воспроизводимость

В закрытом режиме ведущий может добавить явно обозначенных ботов до 3–10 мест. Бот получает ровно PlayerView и legalMoves, не полный state; алгоритм не знает чужих ролей/рук/закрытых целей, кроме собственной разведки. Старатель стремится соединить две жилы и сохранить доступ; предатель — мешать в рамках тех же команд; простая эвристика, случайный fallback и воспроизводимые seed. Бот не ждёт внешнюю AI API. Боты/таймер отправляют те же валидируемые команды. Test harness задаёт seed, сценарии рук/ролей/целей только в изолированном окружении; не включать debug-функции в публичный API.
